## Notable comments, responses, and resolutions

Every review on my Lab 3 PRs included a top-level summary, a checklist of what the reviewer verified, and two or three line comments on the code that carried the most risk. None of the reviews requested changes. The threads below are the ones that raised a question or a follow-up.

### Question on PR #42: two ways to read Attachments

- **Reviewer comment:** On `api-spec.md`, my partner noticed that Ticket Detail embeds `attachments: []` while a standalone `GET /api/tickets/:ticketId/attachments` returns the same metadata, and asked whether the standalone endpoint exists so the UI can refresh only the Attachment list after an upload or removal, or whether it is leftover overlap. The comment was marked non-blocking. [Read the line comment](https://github.com/jakkarin-promsee/toktickit/pull/42#discussion_r4175439134).
- **My response:** TODO — reply in the PR thread, then link the reply here. Suggested answer: the standalone endpoint is intentional and carried over from the Lab 2 Attachment lifecycle, so the client can refresh the list after an upload or soft removal without refetching the whole Ticket; Ticket Detail embeds the same metadata for the first render.
- **Resolution:** Both endpoints are implemented and tested: the Lab 2 Attachment suite covers the standalone list, and API-08 covers the embedded list in Staff Ticket Detail.

### Follow-up on PR #47: extra reference lookups in the Queue

- **Reviewer comment:** My partner noted that the Queue handler runs three extra lookups for inactive-reference checks before the main query, which is fine at this data size and keeps the error behavior exact. [Read the review](https://github.com/jakkarin-promsee/toktickit/pull/47#pullrequestreview-5403820170).
- **Resolution:** Accepted as non-blocking; the exact `400 INVALID_QUERY` behavior for inactive references is covered by API-07.

### Follow-up on PR #48: client copy of the status-transition table

- **Reviewer comment:** My partner pointed out that the client keeps its own copy of the transition table for display while the backend stays authoritative, so both copies must change together if the matrix changes. [Read the review](https://github.com/jakkarin-promsee/toktickit/pull/48#pullrequestreview-5403853984) · [Line comment on the server matrix](https://github.com/jakkarin-promsee/toktickit/pull/48#discussion_r4175772217).
- **Resolution:** Accepted as non-blocking. UNIT-04 tests the server matrix and the client helper separately, and API-10 proves the backend rejects every forbidden pair even if the client copy were wrong.

### Follow-up on PR #49: one lock for every user edit

- **Reviewer comment:** My partner noted that taking the advisory lock before reading the target is what makes the last-active-Administrator check trustworthy, and that a narrower lock would be worth considering if user volume grew. [Read the line comment](https://github.com/jakkarin-promsee/toktickit/pull/49#discussion_r4175812492) · [Read the review](https://github.com/jakkarin-promsee/toktickit/pull/49#pullrequestreview-5403900773).
- **Resolution:** Accepted as non-blocking for the Lab 3 data size. The concurrent-Administrator API test and E2E-04 prove that one active Administrator always remains.

[Read the line comment](https://github.com/jakkarin-promsee/toktickit/pull/51#discussion_r4175927627).
- **Resolution:** Non-blocking and not applied. The Prisma output in every run already prints the target schema, and the isolation rules are documented in `tests.md` section 7.
