# Actions Taken data migration and recovery

Issue #58 adds `ActionTaken`, `ActionEvent`, `ActionCreateRequest`, and `TicketWorkflowEvent` without dropping or rewriting the Lab 1–3 User, Ticket, Attachment, Public Comment, or Internal Note tables. Existing Tickets have zero Actions Taken and remain readable as an empty `data` array. The migration inserts one actorless `BASELINE` workflow event per preexisting Ticket using a deterministic UUID; rerunning the guarded insert cannot duplicate it or change the Ticket status, version, or timestamps.

Before applying the migration to a database with existing data, take a PostgreSQL backup and record row counts for `User`, `Ticket`, `Attachment`, `PublicComment`, and `InternalNote`, plus foreign-key join counts. Run `npx prisma migrate deploy` from `server/`, then compare those counts and verify that representative Tickets still read through the existing API and that a legacy Ticket returns an empty Actions list. The migration SQL contains the guarded baseline insertion for forward recovery; if a later deployment step fails before Action writes begin, restore the backup and previous app build together. Once Action writes exist, do not drop the new tables as a rollback: fix the forward migration and preserve the Action history.

Run the seed with `LAB3_SEED_INITIAL_PASSWORD` set as documented in Lab 3. The seed inserts missing synthetic `example.test` rows and leaves existing rows unchanged. It includes zero, one, and multiple Actions, all Action statuses, different performers on one Ticket, all Ticket statuses and priorities, assigned and unassigned Tickets, and zero/nonzero dashboard cases. `server/tests/lab-04/actions-data.test.ts` verifies repeat runs, an edited fixture surviving a rerun, a representative legacy zero-action Ticket, and a two-run baseline backfill on a disposable legacy-style Ticket.
